Overview

Crossword League is a real-time multiplayer crossword platform built from scratch using vanilla JavaScript, Node.js/Express, and Firebase Realtime Database. It supports up to a dozen concurrent players across five distinct game modes, with a fully featured lobby system, player progression, accessibility tooling, and an in-game moderation layer - no frameworks, no shortcuts.

Problem

Existing crossword games are almost entirely single-player. The challenge was to take a fundamentally single-player format and design it for real-time competition between multiple people - while keeping the core experience of actually solving a crossword intact. That meant solving hard synchronization problems (who owns which cell? what happens when two players guess the same word simultaneously?) without sacrificing feel.

Game Modes
Play Together

Collaborative solving; all players share a live grid.

Versus

1v1 competitive scoring weighted by speed and accuracy.

Ranked Elimination

Players must solve a minimum number of clues each round or get eliminated. Survivors advance; the last player standing wins. A "carry-over" mechanic punishes consistent underperformance across rounds.

Battle Royale

Solving words charges an attack meter. Attacks corrupt opponents' grids (cracking or shattering cells). Players manage a corruption meter and survive through a grace period mechanic. Supports team variants (Red vs. Blue).

Race the Clock

Time-limited solo solve tracked against other players.

Architecture
Frontend

Plain HTML, CSS (custom properties for theming), and ES6 modules - no build step, no bundler, no framework.

Backend

Node.js + Express serving both the API and static assets. Firebase credentials stay server-side and are fetched by clients at runtime via /api/config, so nothing sensitive ships in client JavaScript.

Real-time layer

Firebase Realtime Database. All live game state - grid cells, player cursors, scores, chat messages, elimination state, battle attacks - is synced through Firebase listeners. No polling, no hand-rolled WebSocket server.

Auth

Firebase Authentication with full guest-mode support. Server-side ID token verification via Firebase Admin SDK for protected routes.

Client pattern

Loose MVC: HTML files are pure views with no logic; controller files handle all event wiring; state.js holds shared application state; api.service.js centralizes Firebase and REST calls.

Engineering
Real-time grid sync

Each cell write carries the player ID and color of whoever filled it. Remote writes apply immediately to all connected clients through Firebase listeners. Ranked and battle modes layer additional state (corruption levels, elimination flags) on top of the base grid sync - all without any coordination server beyond Firebase.

Ranked elimination logic

The host client drives elimination rounds on a configurable timer. Each player tracks _rankedCycleWordsCorrect locally; the host compares against the threshold and writes the elimination list to Firebase, which all clients react to simultaneously. An "all-safe" overlay blocks the elimination countdown when every remaining player has already met the threshold - a small detail that prevents eliminations from feeling arbitrary.

Battle corruption system

A 500ms tick increments a corruption meter while a player has unsolved words. Incoming attacks crack or shatter specific cells. Reaching 100% corruption triggers a grace period (temporary invulnerability) rather than instant elimination. Attack targeting supports three modes: Random, Target (click to select), and Payback (auto-targets whoever last attacked you).

Moderation

Bans can be applied at three levels: Firebase UID, device token, or IP address. Optional expiry timestamps support temporary bans. Guest IP join rate limiting (10 joins per IP per 10 minutes) prevents abuse without requiring accounts. A full appeal workflow lets banned players submit appeals stored in Firebase for admin review.

Session integrity

Each device registers an active session at join. Opening the same game in a second tab evicts the first session, preventing the same player from appearing twice in a lobby. Firebase onDisconnect() cleans up presence data automatically on tab close.

Accessibility

Six modes implemented via data attributes on body: light mode, high contrast, colorblind mode, screen reader mode, font size scaling, and dyslexia font selection (OpenDyslexic and Lexend). Because OpenDyslexic renders ~15% taller than Inter at the same pixel size, targeted CSS compensation rules reduce font sizes on compact UI elements to prevent layout overflow - handled entirely in CSS without JavaScript.

Custom keybinds

All game keys (arrow navigation, chat send, hint cycling) are user-configurable and stored as JSON in localStorage. The keybind map is read at runtime wherever a key comparison is made, so remapped keys take effect immediately without a page reload.

Engagement
XP and leveling

Earned through puzzle completions, wins, and chat activity.

Achievements

13+ unlock conditions (win streaks, chat volume, Z-word guesses, ranked survival, etc.) with animated unlock popups.

Weekly Challenges

Three rotating challenges selected per calendar week via a deterministic seed, tracked against a baseline snapshot taken at week start.

Friend system

Friend requests, a friends list, and in-game direct messaging, all backed by Firebase.

Pixel-art avatar creator

A client-side canvas drawing tool for personalizing player icons.

Tech Choices
No framework, no bundler

The entire frontend ships as raw ES6 modules. This was a deliberate choice to keep the architecture transparent and the page load lean - no hydration cost, no tree-shaking complexity, no dependency surface to maintain.

Firebase as the multiplayer substrate

Rather than building a custom WebSocket server, Firebase Realtime Database handles all pub/sub needs. This trades some fine-grained control for massive reliability and latency wins, and eliminates an entire category of infrastructure maintenance.

Procedural audio

Sound effects are generated at runtime using the Web Audio API (sine and sawtooth oscillators with amplitude envelopes) rather than loading audio files. File-based sounds are used only where procedural generation isn't expressive enough, with OGG/MP3 detected per browser.

Outcome

A full-featured, deployable multiplayer game platform with real competitive depth - five distinct modes, a progression system, accessibility support across six dimensions, moderation tooling, and a social layer - built entirely without a frontend framework, a component library, or a managed backend service beyond Firebase.
